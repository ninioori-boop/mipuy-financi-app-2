# אסטרטגיה: WhatsApp כערוץ מרכזי במערכת "הכלכלן של הבית"

מסמך אסטרטגי. מיפוי המערכת הקיימת + מחקר על יכולות WhatsApp Business Platform (2026), וכיצד להפוך את WhatsApp לשכבה שמשפרת את כל המערכת. נכתב 2026-07-25.

---

## 1. התזה המרכזית

**WhatsApp לא מחליף את האפליקציה. הוא הופך לשכבת הקלט/פלט הכי נגישה שמעליה.**

הבעיה מספר 1 בליווי פיננסי אישי היא לא ניתוח, אלא **הזנת נתונים ומעורבות**: לקוחות לא נכנסים לאפליקציה לתעד כל קנייה, ולא בודקים תקציב באמצע היום. WhatsApp פותר בדיוק את זה, כי הלקוח כבר שם כל היום.

הרעיון:
- **קלט:** הלקוח מתעד ("קניתי ב-50 בסופר") ושואל ("כמה נשאר לי לאוכל?") בצ'אט, בלי לפתוח כלום.
- **עיבוד:** אותה צנרת קיימת (קטגוריזציה, inbox, flywheel) מטפלת בזה. הנתונים זורמים לאותו Firestore.
- **פלט עמוק:** האפליקציה נשארת למקום שבו רואים את התמונה המלאה (גרפים, מיפוי, תכנון שנתי).
- **הלולאה האנושית:** היועץ (אתה) מקבל התראות וסיכומים בצ'אט, ופועל.

השורה התחתונה: WhatsApp מוריד דרמטית את החיכוך של תיעוד ומעורבות, מזין את אותו מקור אמת יחיד, והאפליקציה + היועץ נשארים שכבת העומק.

## 2. המודל הכלכלי (קובע את כל העיצוב)

מ-1 ביולי 2025 Meta עברה לתמחור **per-message**, והחלוקה הזאת חייבת להכתיב את הארכיטקטורה:

| סוג הודעה | מתי | עלות |
|-----------|------|------|
| **Service** (הלקוח יזם, בתוך 24 שעות) | הלקוח כתב לבוט → 24 שעות של שיחה חופשית | **חינם** |
| **Utility** (תבנית טרנזקציונית) | תזכורת/עדכון יזום. חינם אם בתוך חלון ה-24 שעות | זול מאוד (~0.4-4.5 אג') |
| **Marketing** (תבנית שיווקית) | קידום/שיווק יזום | יקר (~2.5-13.6 אג'), בלי הנחות כמות |

**עקרונות עיצוב שנגזרים מזה:**
1. **בנה סביב אינטראקציות שהלקוח יוזם** (תיעוד + שאילתות) → כמעט הכל חינם.
2. **הודעות יזומות = Utility בלבד**, ממוקדות ומעטות (התראת חריגה, תזכורת חודשית). לעולם לא Marketing.
3. **כל תזכורת יזומה פותחת חלון 24 שעות** — נצל אותו: התזכורת מזמינה את הלקוח להגיב, וכל ההמשך חינם.

> המשמעות: בקנה המידה שלך (עשרות לקוחות, מעט הודעות יזומות לחודש לכל אחד), העלות הצפויה היא **בודדים עד עשרות שקלים בחודש**, לא יותר.

## 3. הארכיטקטורה — מה כבר קיים ומה חסר

### מה כבר בנוי (מנוף ענק, אין צורך לבנות מחדש)
- **`/api/transaction`** — endpoint תיעוד ההוצאות. כבר מטפל ב"הודעה אחת → הוצאה מסווגת": פרסינג של טקסט חופשי מבולגן, dedup, זיהוי העברות (ביט/פייבוקס), הגנות echo, ומחזיר טקסט אישור מודע-תקציב. **זה משטח השימוש-החוזר הכי עשיר.**
- **`transactionInbox/{uid}/items`** — כל מה שנכתב לשם **נצרך אוטומטית** ע"י האפליקציה (hook `useTransactionInbox`, persist-before-delete). כלומר בוט שכותב לשם — האפליקציה מתעדכנת לבד, בלי שינוי בצד לקוח.
- **מנוע קטגוריזציה + flywheel** — `learnedDB → BUSINESS_DB → AI`. כל תיקון מזין את כולם.
- **`goalBot.js`** — אינטגרציית WhatsApp Cloud API שלמה ומבודדת להעתיק ממנה (שולחים, verify, dedupe, פרסינג עם Claude).
- **מערכת יועץ-לקוח** — הזמנות, הסכמה, שלבים, view-as-client, digest שבועי (מנוע ההודעות היזומות הקיים, במייל).
- **מנגנון device-token → custom-token** (`/api/app-session`) — בדיוק התבנית לחיבור זהות.

### הפער היחיד המשמעותי: **זהות (phone ↔ uid)**
היום אין מיפוי בין מספר טלפון למשתמש. ל-goalBot יש `WHATSAPP_TO` קשיח (משתמש יחid). בוט ללקוחות חייב:
1. **קולקציה חדשה** `whatsappLinks/{phone} → uid`.
2. **תהליך חיבור חד-פעמי:** הלקוח נכנס לאפליקציה → מקבל קוד → שולח אותו לבוט פעם אחת → המספר נקשר ל-uid. (מראה את התבנית של `/api/app-session`.)
3. **ניתוב רב-דיירי:** הבוט מזהה לפי מספר השולח לאיזה uid לכתוב.

### זרימת הודעה (client bot)
```
לקוח שולח וואטסאפ
   → webhook (Firebase Function, כמו goalBot)
   → זיהוי: whatsappLinks[from] → uid   (אם לא מקושר → תהליך חיבור)
   → Claude מפרש: תיעוד הוצאה? שאילתה? תיקון?
   → תיעוד:   כותב ל-transactionInbox/{uid}/items  → האפליקציה נצרכת לבד
     שאילתה:  קורא מ-users/{uid}.data → מחזיר סיכום + קישור לאפליקציה
   → מזין את learnedDB (flywheel)
```

## 3.5 וייט-לייבל ורב-דיירי (multi-tenant)

**עיקרון מנחה: לבנות tenant-aware מהיום הראשון.** רטרו-פיט של רב-דיירי כואב; בנייה נכונה מראש כמעט חינם, כי **השלד כבר קיים** — כל קישור לקוח נושא `practiceId` + `invitedByUid`.

### ההיררכיה
```
פלטפורמה (אתה)
  └─ פירמה = practices/{practiceId}      ← הדייר בוייט-לייבל
       └─ יועץ = advisors/{uid}
            └─ לקוחות = clientLinks/{clientUid}   (נושא practiceId + invitedByUid)
```

### איך הבוט מנתב
- **לקוח** שולח → `phone → uid → clientLinks[uid]` → מקבל יועץ (`invitedByUid`) + פירמה (`practiceId`).
- **יועץ** שולח → `phone → uid → advisors[uid].practiceId` → מציג **רק** לקוחות ש-`invitedByUid == היועץ`. יועץ בפירמה A לעולם לא רואה לקוחות של פירמה B. בידוד נאכף ב-`firestore.rules`.

### ההחלטה המרכזית: מספר WhatsApp
| | מספר פלטפורמה אחד | מספר לכל פירמה |
|---|---|---|
| ניתוב | לפי זהות (`phone→uid→practice`) | לפי `phone_number_id` שאליו נכנסה ההודעה → `practiceId` |
| מיתוג | שם הפירמה בגוף ההודעה בלבד | הלקוח רואה את המספר והשם של הפירמה = וייט-לייבל אמיתי |
| מורכבות/עלות | פשוט וזול | מספר+WABA לכל פירמה (הכל תחת ה-Meta Business שלך, מודל BSP) |

**המלצה:** מספר אחד עכשיו (ניתוב לפי זהות), אבל לכתוב את ה-webhook כך שהוא כבר קורא `phone_number_id` וממפה ל-`practiceId` — כך שמעבר למספר-לכל-פירמה הוא **שינוי הגדרה, לא כתיבה מחדש**.

### מה נדרש כדי להיות tenant-aware
1. זיהוי זהות תמיד מחזיר גם `practiceId`.
2. כל read/write של הבוט מסונן לפי הפירמה.
3. הגדרה per-firm על `practices/{id}`: שם, לוגו, צבעים, סט תבניות, ומספר WhatsApp.
4. `firestore.rules` אוכפים בידוד ברמת הפירמה, לא רק הלקוח.
5. האפליקציה טוענת מיתוג לפי `practiceId` — override של ה-tokens ב-`globals.css` לכל דייר.

> מתחבר ישירות לעסקת ה-SaaS (240₪/לקוח/שנה למשרד ייעוץ): הבוט והאפליקציה חייבים להיות רב-דייריים כדי לתמוך בה.

## 4. תרחישי שימוש — ממופים למערכת

### A. לקוח — קלט (תיעוד) · *הלקוח יוזם = חינם*
| תרחיש | מתחבר ל | סטטוס טכני |
|--------|---------|-------------|
| "קניתי ב-50 בסופר" → הוצאה מסווגת | `/api/transaction` → `expenseLogStore` | reuse ישיר |
| העברת SMS/קבלה של חיוב → פרסינג ותיעוד | אותו endpoint | reuse |
| צילום קבלה → OCR → תיעוד | מסלול `automap`/`/app/ingest` | קיים חלקית |
| הודעה קולית → תמלול → תיעוד | Claude + תמלול | עתידי |

### B. לקוח — שאילתות (קריאה) · *הלקוח יוזם = חינם*
| תרחיש | מתחבר ל |
|--------|---------|
| "כמה הוצאתי החודש?" / "כמה נשאר בתקציב אוכל?" | `monthlyStore` + `categoryBudgetStore` → סיכום + קישור |
| "מה המצב שלי?" | לוגיקת `SafeToSpendToday` / health |
| "מה המטרות שלי?" (הכללה של goalBot לכל לקוח) | `goalsStore` |

### C. לקוח — תזכורות יזומות · *Utility, במשורה*
| תרחיש | מתחבר ל |
|--------|---------|
| "עברת 80% מתקציב אוכל" | `categoryBudgetStore` + חריגה |
| סיכום שבועי/חודשי | `monthlyStore` |
| תזכורת חידוש מנוי | זיהוי מנויים (`subscriptions`) |
| תזכורת בקרת תקציב (ה-28) | `BudgetReviewReminder` |
| תזכורת משימה/פגישה | `meetingsStore.tasks` |

### D. לקוח — Onboarding ואיסוף נתונים · *WhatsApp Flows*
WhatsApp Flows = טפסים אינטראקטיביים מלאים בתוך הצ'אט (כפתורים, רשימות, שדות, בוחר תאריך):
- **טופס intake** כ-Flow (מראה את `intakeForm.ts`).
- **הקמת תקציב / מטרות** מודרכת ב-Flow.
- **הסכמה + שיתוף** (opt-in) כ-Flow.
- **בקשת העלאת מסמכים** → קישור ל-`upload-guide`.

### E. יועץ (אתה) — הקוקפיט של המאמן בצ'אט
| תרחיש | מתחבר ל |
|--------|---------|
| "מה קורה עם עדן?" → סיכום לקוח | `advisorClients` / dashboard |
| התראת דגל אדום (לא עודכן 30 יום, חריגה) — בזמן אמת | הרחבה של `weeklyAdvisorDigest` |
| "תוסיף פגישה עם X, משימה: להביא דוחות" | `meetingsStore` (כמו skill add-meeting, בצ'אט) |
| אישור/הזמנת לקוח, קידום שלב | `inviteClient` / `setClientStage` |

### F. מערכת — ה-flywheel
- כל הוצאה שתועדה בוואטסאפ מזינה את `learnedDB` + `aiSuggestions` → קטגוריזציה טובה יותר **לכל הלקוחות**.
- תיקון בצ'אט ("זה לא אוכל, זה בילויים") → `/api/learn`.

## 6. זהות, פרטיות ואבטחה (קו אדום למערכת פיננסית)

- **חיבור זהות:** קוד חד-פעמי מהאפליקציה → הבוט. בלי זה, כל אחד ששולח יכול לבקש נתונים.
- **מה לא שולחים בצ'אט:** לא מספרי חשבון מלאים, לא פירוט רגיש מלא. שולחים **סיכומים + קישור מאובטח לאפליקציה** לצפייה מפורטת. WhatsApp מוצפן בהעברה, אבל גיבויים בענן לא בהכרח, וזה ערוץ צד-שלישי.
- **opt-in מפורש:** חובה לפני כל הודעה יזומה. מנוהל דרך flow ההסכמה + `clientLinks`.
- **בידוד רב-דיירי:** לעולם לא לדלוף נתוני לקוח A ללקוח B. ניתוב לפי מספר מאומת בלבד.
- **תאימות:** הסכמה, שקיפות על שימוש בנתונים, שמירת תיעוד תקשורת (GDPR).
- **כנות ב-UI:** אם משהו לא אוטומטי — לומר את זה. לא לטעון "נשלח" אם לא נשלח.

## 8. סיכונים ושאלות פתוחות
- **אישור תבניות** — חיכוך ועיכוב (ראינו בבוט המטרות). לתכנן מראש, נוסח transactional.
- **מספר פרודקשן + אימות עסק** — למעבר ממספר בדיקה ליציב בקנה מידה.
- **פרטיות נתונים פיננסיים** בערוץ צד-שלישי — לתכנן סביב (סיכומים+קישורים).
- **ניהול opt-in** — מי הסכים, מתי, ואיך מבטלים.
- **ToS/חסימות** — Cloud API רשמי מפחית סיכון; לא להשתמש בכלים לא-רשמיים.

## 9. למה זה הופך את המערכת ל"כמה שיותר טובה"

1. **מוריד את החיכוך הגדול ביותר** (תיעוד ומעורבות) — הלקוח פועל מהמקום שהוא כבר בו.
2. **מזין מקור אמת יחיד** — אותו Firestore, אותה קטגוריזציה, אותו flywheel. אין ממשק מנותק.
3. **מחזק את ה-flywheel** — יותר נתונים → קטגוריזציה טובה יותר לכולם.
4. **מכפיל את היועץ** — סיכומים והתראות בזמן אמת בצ'אט הופכים אותך ליעיל פי כמה.
5. **האפליקציה נשארת שכבת העומק** — WhatsApp הוא הקלט/פלט המהיר, האפליקציה היא הניתוח, אתה הלולאה האנושית.

הבוט האישי (שלב 0) כבר הוכיח שהצינור עובד. השלב הבא בעל הערך-מול-מאמץ הכי גבוה: **שלב 1 — תיעוד ושאילתות ללקוח, מעל `/api/transaction` הקיים.**
